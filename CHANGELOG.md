# Changelog

Todos los cambios relevantes de Iris se documentan en este archivo.

El formato sigue [Keep a Changelog](https://keepachangelog.com/es-ES/1.1.0/) y el proyecto usa [Versionado Semántico](https://semver.org/lang/es/).

Cada entrada termina con el ID de la tarea del backlog (`docs/roadmap/`). Secciones permitidas: `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security`.

## [Unreleased]

### Added
- **The outage history is paged, searchable and has its own period.** It used to list every outage of the page's period at once, a list that only grows. It is now its own section with a table (service, state, start in UTC, duration or *ongoing*, cause), 10 per page with Previous/Next and the total, a **search** (service, cause or description, sent 300 ms after the last key), **service** (the same filter as the health cards) and **state** filters, and a **period**: the page's, 24 h, 7, 30 or 90 days, or dates of its own (UTC, validated: start before end, within the 90 days Mercury keeps). Everything is filtered and paged by Mercury. The BFF passes `from`, `to`, `q`, `service`, `status`, `page` and `size` on `/monitoring/outages`, validated (`q` up to 100 characters without control characters; dates as `2026-11-16T10:00:00`; status `DOWN`/`DEGRADED`; else 400). **Requires** Mercury with the paged outage history (um-dev-creative/mercury#111). See `docs/technical/monitoring.md` and `docs/user/manual-operador.md`.
- **Monitoring charts redesigned: compact, interactive and validated.** The sends-over-time chart is drawn in real pixels with a fixed height (it no longer grows with the screen width), as smooth monotone lines that pass exactly through every value (or stacked columns, remembered per browser), with a separate, aligned **failure-rate** chart on its own scale instead of a second axis. A crosshair snaps to the nearest interval on both charts with a readout (window, sent, failed, failure rate) and the legend follows it; click, or Enter from the keyboard (arrows, Home/End, Escape), filters the page by that interval; the in-progress interval is dashed and labelled; end-of-line values only when they don't collide; a **table view**; the frame holds and dims while refreshing. The summary leads with the success rate as a 48 px figure, a same-hue meter and a status with icon and text (Healthy ≥ 95 %, Attention ≥ 80 %, Critical); sent and failed tiles carry their period trend (`trend-spark`). Channels and kinds are a meter list with thin segmented bars, failure causes are ranked bars with the value at the tip, and verification codes use a tall segmented bar with in-block shares where they fit. New data-series colors `--viz-sent`, `--viz-failed`, `--viz-waiting` (light and dark) pass the palette validator (the previous `--chart-2`/`--chart-5` pair did not). The success ring is removed. Verified visually in headless Chrome (light/dark, lines/columns, 1 h/24 h/30 d, desktop and 390 px) with no console errors. See `docs/technical/monitoring.md`.
- **Social sign-in with Google, Microsoft, Apple, GitHub and Meta** (off by default, `FEDERATION_ENABLED=true`). The login page shows *Continuar con …* buttons for the providers the application offers; the BFF (`/mrc/api/v1/auth/federation/*`) asks Backbone — the identity broker — to start the sign-in, keeps the single-use `state` in an `httpOnly` cookie (`SameSite=Lax`; `None` only for Apple's cross-site form POST, which is exempt from the CSRF header and bound by that cookie and Backbone's state), validates `returnTo` against `FEDERATION_RETURN_TO_ALLOWLIST`, maps Backbone's stable error codes to login messages and sets the same session cookies as the password login. Only existing users sign in. New page **Mi cuenta** (`/dashboard/account`, menu link) lists the linked accounts, links another provider and unlinks one with confirmation. A federation 403 from Backbone is about the person, not a misconfigured application client. **Requires** Backbone with the federation (migration `V10`, persistence/commons 0.0.4, a provider setting whose redirect URI equals `FEDERATION_CALLBACK_URL`); `settings-check` refuses to start with the flag on and no callback URL. BFF tests 308 (functions 99 %), Angular tests 842 (functions 91.8 %). See `docs/technical/social-federation.md`, `docs/technical/security.md` and the operator manual (*Entrar con una cuenta externa*). Requirements and design live in `backbone-rest/docs/`.
- **Livelier, more precise monitoring charts.** The sends-over-time chart gets a value axis with round ticks and guide lines, a period summary (total, sent, failed, peak), a hover/focus tooltip per bar (UTC window, sent, failed, failure rate) and a hatched, labelled **in-progress** last bucket so an incomplete interval is not read as a drop; bars grow in and change height smoothly when data arrives. Summary figures count up to their new value and flash green/red when they improve/worsen (`animated-number`); the success ring animates and turns green (≥ 95 %), amber (≥ 80 %) or red, and says "N of M delivered"; new accessible proportion bars (`ratio-bar`) on the summary, every channel (with its share of the volume), kind, failure cause and the verification codes. The "live" dot and a down service pulse. Everything respects `prefers-reduced-motion`. See `docs/technical/monitoring.md`.
- **Template preview that matches the e-mail that is sent.** The preview shows the rendered **subject** (as Mercury's `SubjectRenderer` resolves `${x}` / `${x!"fallback"}`, warning about parameters without a sample value), a **Desktop / Mobile** width toggle, a frame that fits the e-mail's height, a warning for parameters with no sample value, and an "Updating… / Up to date / errors" state. With a syntax error it keeps the **last valid preview**, dimmed, instead of going blank, and a late answer to an older request can no longer overwrite a newer one. The frame's sandbox is `allow-same-origin` only (no scripts, forms or pop-ups) so its height can be read. See `docs/technical/templates.md`.
- **Monitoring section, phase 4: alerts, retry of failed e-mails and export.** The monitoring page gets a red banner with the alerts that are firing, an **Alertas** section (rules with enable/disable and delete, a validated form for a new rule, and the latest resolved alerts), a **Reintentar** button on failed e-mails of the message table, and **Exportar CSV/JSON** of the table with the active filters (the file reports when it was cut). A rule watches the failure rate over a window, messages waiting longer than a window, or a service degraded or down; it can e-mail up to 5 addresses. The BFF adds `GET /mrc/api/v1/monitoring/alerts`, `GET|POST /alerts/rules`, `PUT|DELETE /alerts/rules/:id`, `POST /messages/:id/retry` and `GET /messages/export`: the application is fixed by the BFF, only the documented query parameters and rule fields pass (a bad type or a non-UUID id is a `400`), writes need the CSRF header, and `Content-Disposition` and `X-Export-Truncated` are passed back and exposed through CORS. **Requires** Mercury with monitoring phase 4 (V2041, branch `feat/monitoring-phase4-alerts-retry-export`) and, to retry or manage rules, `mercury:message:write` in `BACKBONE_CLIENT_SCOPES` (registered on the Backbone M2M client first); without it Mercury answers `403`. See `docs/technical/monitoring.md` and `docs/user/manual-operador.md`.
- **Monitoring section: a live, linked view of sends, failures, verification codes and service health.** New page `/dashboard/monitoring` (menu entry *Monitoreo*; the home page links to it) with a period selector (1 h, 24 h, 7 d, 30 d), summary cards with the success-rate ring, per-channel and per-kind cards, a sent/failed bar chart over time, top failure causes and stuck queues, verification-code figures, the state of SMTP, Kafka, MongoDB, PostgreSQL, Backbone and Telegram with the cause and the outage history, and a paged message table with masked recipients. The views are linked: choosing a channel, a kind, sent/failed, a bar or a failure cause filters the others and the table, and a service filters the outage history. Data arrives through Mercury's Server-Sent Events stream (summary and health every 10 s) and is polled every 30 s for the rest; when the stream is refused the page polls everything every 15 s and retries the stream every minute. Without data it shows no figures, without sends no rate, channels with no provider read "queued, no provider", and a failed refresh shows a "may be out of date" warning. Charts are own SVG (no library). **Requires** Mercury with monitoring phases 1 and 2 (PRs #103 and #104). The BFF adds `GET /mrc/api/v1/monitoring/{summary,series,failures,verification-codes,messages,health,outages,stream}`: the application is fixed by the BFF, only the documented query parameters pass (anything else is a `400`), the stream is passed through without buffering or compression, and `compression()` skips `text/event-stream`. Behind nginx, turn off proxy buffering for `/monitoring/stream`. See `docs/technical/monitoring.md` and `docs/user/manual-operador.md`.
- **El editor de plantillas define el asunto del correo.** El formulario de crear y editar una plantilla de una aplicación tiene el campo **Asunto del correo** (opcional, 500 caracteres, con datos del mensaje como `${vc}`); se guarda en la plantilla de Mercury (`subject`, una por idioma) y Mercury lo usa al enviar, de modo que las aplicaciones ya no lo llevan en su código. El BFF deja pasar `subject` en crear y editar. **Requiere** Mercury con el asunto de plantilla (PR #90); contra uno anterior el campo se ignora. Ver `docs/technical/templates.md`.
- **Sección «Usuarios»: dar y quitar el acceso de una persona a una o varias aplicaciones, y crear usuarios.** Se elige la aplicación, se ven sus usuarios y de cada uno a qué aplicaciones entra y con qué rol. Es la base para tener administradores de plantillas de una o varias aplicaciones y administradores de la plataforma (`PLATFORM_ADMIN`). El BFF añade `/bkd/api/v1/admin/*` (sesión como `Authorization: Bearer`, ids UUID, campos permitidos al crear). Ver `docs/technical/access-administration.md` y `docs/user/manual-operador.md`.
- Plantillas por aplicación: en **Plantillas** se elige primero la aplicación (`/dashboard/templates`), luego se ven sus plantillas (`/dashboard/templates/:applicationId`) y de ahí se abre el editor (`/dashboard/templates/:applicationId/:id` y `/new`), con ruta de migas para volver. El BFF añade `GET /templates/applications` (aplicaciones de Backbone) y las rutas `/templates/applications/:applicationId` (lista, crear y vista previa), que toman la aplicación de la URL y no necesitan `MONITORED_APPLICATION_ID`. Mercury guarda cada aplicación en su carpeta (`lth/mercury/templates/<aplicación>/`), así que lo que se edita aquí es el mismo archivo que usa para enviar.

### Changed
- **Templates open instantly after saving.** `TemplatesService` keeps an in-memory, per-tab copy of what it read or saved (template data, content, the sample parameters the person typed, list searches, the last 20 previews for 1 min); the editor opened right after creating a template draws at once (no "Cargando plantilla…", same sample values, preview without a new request) and confirms with the server in the background without overwriting what is being typed. Editing saves the metadata and the content in parallel instead of one after the other. `ReferenceDataService` asks for types and severities, and `TemplatesService` for applications, once per session (again if the first try failed). The template list draws the last answer of the same search at once with a thin "updating" bar, shows a skeleton on first load, and each row shows its format (Markdown/HTML), its subject, a relative "updated" time and a **Recién guardada** badge for the template saved in the last 2 minutes.
- **El selector de aplicaciones de Plantillas muestra solo las que la persona puede gestionar.** Lee `GET /mrc/api/v1/templates/applications` de Mercury (todas para un administrador de la plataforma; las que tienen `TEMPLATE_MANAGE` para el resto) en vez de todas las de Backbone.

- El showcase de componentes (enlace del menú y ruta `/dashboard/showcase`) solo existe fuera de producción: `features.showcase` sigue a `production` salvo que el entorno lo defina, y en producción la ruta redirige al dashboard.

### Fixed
- **The monitoring covers every send of Mercury, whoever sent it, and says when Mercury is not recording.** The monitoring is Mercury's own, not one client's, but the page only showed the application of Iris, so what a client of Mercury such as ZeroBound sends (recorded under *its* application) never appeared and the page looked empty although Mercury had sent the e-mail. Without a choice the BFF now asks Mercury for **all applications** (the nil UUID; `MONITORED_APPLICATION_ID` is no longer needed by the monitoring), and the page has an **Aplicación** selector (**Todas las aplicaciones** or one of the applications Mercury lists for the person, `/templates/applications`) that narrows every view, the live stream, the export, the retry and the alert rules and clears the filters. The BFF adds `GET /mrc/api/v1/monitoring/applications` and accepts `applicationId` on every monitoring route: not a UUID is `400`, an application the person may not look at is `403` (the list is read once a minute per session). A red banner explains an empty page when Mercury reports (`health.storage`) that its monitoring tables are missing (migrations `V2039` to `V2041` not applied), naming them, and a warning shows how many recordings failed. **Fixed:** when Mercury could not compute the summary it sends `{"error": ...}` in the `summary` event and the page crashed (`Cannot read properties of undefined (reading 'successRate')`); such an event now leaves what is shown as it is and marks it as possibly out of date. **Requires** Mercury with the all-applications scope and the storage check. See `docs/technical/monitoring.md`.
- **The «Servicio caído» alert rule offered service names Mercury rejects.** The form listed `POSTGRES` and `MONGO` but Mercury reports and accepts `POSTGRESQL` and `MONGODB`, so a rule for the databases could not be created (400). The list now matches Mercury's health names. Found by running the whole flow (Iris BFF and page against a real Mercury, PostgreSQL, MongoDB, Kafka and SMTP).

- **The reason a service gives for refusing a creation (for example, that the record already exists) is now shown to the person.** Backbone sends it in the `Message-header` or `Warning` response header with an empty body (`User previously exist.`, `E-mail previously exist.`, `Role name previously exist.`), and the BFF dropped both headers, so the person saw nothing useful. `server/shared/proxy.js` now passes them back (plain printable text, at most 300 characters; anything else is dropped) and they are exposed through CORS. In the frontend, the new `serviceMessage()` (`core/utils/service-message.ts`) reads the reason from the body (`message`, `error`) or from those headers; `httpErrorInterceptor` shows a `409` as **Ya existe** with that reason instead of the generic "unexpected error", and the campaign, template and login-client forms show it too. A `409` with no reason keeps a fixed text. Covered by `proxy.spec.js`, `service-message.spec.ts`, the interceptor and the campaign/login-client specs. See `docs/technical/backend.md` and `docs/user/manual-operador.md`. The Users section (PR #68) gets it through the interceptor once merged.
- Cuando el panel de monitoreo muestra un servicio como «Down», el BFF ahora dice por qué en el log (`Monitoring: the Backbone health probe /… answered 401`, o el código de error si no hubo respuesta): un 401, 403 o 404 indica una ruta equivocada en `BACKBONE_HEALTH_PATH` o `MERCURY_HEALTH_PATH`, no una caída.
- Entrar en **Plantillas** ya no devuelve al login: la lista de aplicaciones (`GET /templates/applications`) se pedía a Backbone con el encabezado `session-token`, pero los recursos de backbone-rest solo leen la sesión de `Authorization: Bearer`, así que respondía 401 y el navegador cerraba la sesión. El BFF envía ahora la sesión también como `Bearer` (opción `bearer` de `proxyToApi`, que sigue a una sesión renovada).
- El panel de monitoreo ya no muestra Backbone como «Down» cuando está arriba: sondeaba `/actuator/health`, que backbone-rest protege con sesión (401), y ahora usa la sonda pública `/actuator/health/readiness` (`BACKBONE_HEALTH_PATH`).
- El dashboard ya no te devuelve al login cuando Mercury rechaza una sesión que Backbone da por activa (p. ej. Mercury con otro `APP_TOKEN_SECRET`): el panel carga sin campañas y el BFF avisa en el log. Un 401 solo cierra la sesión si Backbone también la rechaza.
- Sign-up asks backbone for the `users:manage` scope (`BACKBONE_CLIENT_SCOPES`), which `UserAdminGuard` requires to check e-mails and create and activate users; the docs state that the M2M client must belong to `BACKBONE_APPLICATION_ID`.

### Security

- Iris corre en HTTPS: `ng serve` y el BFF usan en local un certificado autofirmado (`scripts/dev-cert.mjs`), las cookies de sesión llevan `Secure` y en producción el BFF no arranca sin `COOKIE_SECURE=true`.
- `multer`, `axios` and `express` updated: `pnpm audit --prod` reports no known vulnerabilities.
- Sign-up never takes the role, application or active state from the browser, and does not reveal which e-mails have an account.
- Las cookies de sesión del BFF (`iris_session`, `iris_refresh`) pasan de `SameSite=Lax` a `SameSite=Strict`; se agregaron pruebas de sus atributos, de la respuesta genérica ante credenciales inválidas y de que la sesión sobrevive a un reinicio. (F2-01)
- Las acciones de GitHub del pipeline de CI se fijan por SHA de commit completo (con el tag como comentario). Seguimiento de SonarCloud S7637.
- Los logs del proxy ya no incluyen datos de la petición (ruta ni URL), la renovación de sesión se extrajo a `renewSession` y el límite de subida bajó a 8 MB. Seguimiento de SonarCloud.
- El proxy del BFF rechaza con 400 rutas con segmentos `..`, `//` inicial, barras invertidas o caracteres de control; los logs saneados evitan inyección de líneas; la subida multipart limita archivos, campos y partes. Se resolvieron los hallazgos de SonarCloud.
- Se retiró `default.env` del control de versiones, se agregó `default.env.example` y se ampliaron las exclusiones de `.gitignore` para secretos y llaves TLS. (F0-01)

### Changed

- `packageManager` pasa a `pnpm@12.15.0`: con 12.11.2 fijado, el pnpm 12.15.0 que lanza corepack abortaba `pnpm dev` con `ERR_PNPM_BAD_PM_VERSION`.
- Redundant scripts removed: `server`, `watch:ssr`, `dev:integrated:unix`, `dev:integrated:win`, `scripts/start-dev.sh`, `scripts/serve-integrated.sh` and `scripts/build-test.sh`. Use `pnpm dev` or `pnpm start:bff`.
- **Settings from `local.env` or Vault:** the BFF reads `secrets/local.env`, then `config/local.env` and, with `VAULT_ENABLED=true`, Vault, which fills only what is still empty. Local runs and Docker use the same files, as Mercury and ZeroBound do, and Kubernetes builds `iris-secrets` from `secrets/local.env`. `default.env`, `.env.docker` and `.env.secrets` are gone; `.env` is only for Compose substitutions. `docker-compose.yml` now sets the port, the service URLs and the internal CA. `pnpm start:bff` loads both files in `package.json` and `pnpm dev` runs `ng serve` and the BFF together.
- `authGuard` protege el dashboard con la sesión real y se agrega `guestGuard` para `/login`. (F2-05)
- Todos los entornos consumen la API a través del BFF con URL relativa; se agregaron configuraciones de build para dev, qa y cloud. (F1-05)
- `build:ssr` compila el target de servidor con el mismo `ENVM` (antes siempre con `production`). (F1-05)
- La configuración de la aplicación se inyecta mediante `APP_CONFIG` y `API_BASE_URL`. (F1-03)
- Las rutas de la aplicación se definen en constantes tipadas (`ROUTE_PATHS`). (F1-02)
- BFF reescrito con el patrón de Stratum y zerobound-frontend: `createApp()` sin efectos, configuración por variables de entorno con validación de arranque, sesión por cookies httpOnly con renovación automática, protección CSRF por cabecera, trazas W3C, proxies a Mercury y Backbone y pruebas (≥ 85 %). Rutas `/mrc/api/v1/*` y `/bkd/api/v1/*` conservadas; el login (`access-token`) ahora usa solo la sesión de Backbone. (F0-02)
- El servidor se arranca desde un único punto (`createApp` en `server/app.js`); `server.js` queda como lanzador que valida la configuración. (F0-03)
- pnpm es el único gestor de paquetes (`packageManager`, `engines`, lockfile versionado); documentación histórica reorganizada en `docs/history/` y scripts en `scripts/`. (F0-05)
- Las pruebas usan Vitest con un umbral mínimo de cobertura del 85 % en frontend y backend. (F0-06)
- Pruebas del frontend existente (servicios, interceptor, componentes compartidos, layout y páginas) con ≥ 85 % de cobertura; `showcase-page` queda excluida. (F0-07)
- Actualización a Angular 22.2.3 con TypeScript 6.0.

### Fixed
